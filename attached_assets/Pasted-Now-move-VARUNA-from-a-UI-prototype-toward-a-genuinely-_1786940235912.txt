## GOAL

Make the existing "Timing Channels" module execute a real timing side-channel experiment against a deliberately vulnerable C function and return real measurements to the existing VARUNA UI.

The flow should be:

C target
→ compile
→ timing harness
→ collect timing samples
→ compare two input groups
→ Welch's t-test
→ determine result
→ send real result to VARUNA API
→ display it in the existing Timing Channels page.

## 1. Create a controlled vulnerable C target

Create a small self-contained C example demonstrating a non-constant-time secret/token comparison.

Use an intentionally early-exit comparison so that different inputs can produce measurable timing differences.

Keep this target isolated inside a dedicated prototype/demo target directory.

Example concept:

secret/token
→ compare character by character
→ return immediately on mismatch

DO NOT use a real password, credential, or external target.

## 2. Create a timing harness

Implement a real timing harness that:

- executes the vulnerable function repeatedly
- measures execution time using a high-resolution monotonic timer
- creates two clearly defined input groups
- collects thousands of measurements
- outputs raw timing samples
- records sample count
- records mean/median where useful
- records variance/std deviation where useful

Make the number of samples configurable.

Start with approximately 10,000 samples per group, but make this configurable through the API.

The harness must produce real measurements, not seeded/random demo values.

## 3. Welch's t-test

Implement the statistical analysis using Python and scipy.stats.ttest_ind or an equivalent correct implementation.

Use Welch's version rather than assuming equal variance.

Return at minimum:

- sample count for group A
- sample count for group B
- mean timing A
- mean timing B
- t-statistic
- p-value
- configured threshold
- interpretation/status

Possible states:

- LEAKAGE_DETECTED
- NO_SIGNIFICANT_LEAKAGE
- INCONCLUSIVE
- NOT_RUN
- ERROR

Do NOT hardcode a threshold without documenting it.

Make the threshold configurable.

## 4. Handle real-world timing noise

Do not assume the timing difference will automatically be obvious.

The experiment should account for:

- system scheduling noise
- compiler optimization
- CPU frequency changes
- measurement overhead

Compile the vulnerable target appropriately so the intended early-exit behaviour remains observable.

If the first implementation produces unreliable statistical separation, improve the experimental harness rather than fabricating a stronger t-statistic.

The goal is reproducibility.
