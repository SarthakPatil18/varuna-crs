Mission

Create a production-grade, enterprise-quality web application for VARUNA, a Graph-Guided Autonomous Cyber Reasoning System.

VARUNA is a cybersecurity analysis and remediation platform designed to:

Analyze C/C++ code and target binaries

Build a Code Property Graph (CPG)

Use GraphSAGE-based GNN prioritization to identify suspicious functions, nodes, and security-critical regions

Detect timing side-channel vulnerabilities using TVLA/Welch's t-test

Analyze and fuzz undocumented/custom binary protocols using structure-aware, field-aware mutations

Use a local LLM for vulnerability explanation and patch generation

Re-run security analysis after patching

Validate whether the vulnerability signal has been reduced or eliminated

Present evidence, findings, patches, attack paths, and verification results through a unified dashboard

The application is a working cybersecurity analysis tool, not a marketing website or static mockup.

The provided visual reference image should be treated as the source of truth for the visual direction, layout, spacing, hierarchy, and overall interface appearance. Do not invent a different visual language.

Core Product Workflow

The primary VARUNA workflow should be:

Target Upload → Analysis → Graph/Threat Prioritization → Security Analysis → Finding → Patch → Re-verification → Report

The system must clearly communicate what VARUNA is currently doing and what evidence has been produced.

A typical analysis should progress through:

Target uploaded

Target validated

Code/target parsed

Code Property Graph generated

GNN prioritization performed

Security-critical regions identified

Timing analysis and/or protocol fuzzing executed

Vulnerability detected

Evidence collected

Patch generated or applied

Same security test re-run

Regression/security validation completed

Final result generated

GNN Prioritization

The GNN is a prioritization layer.

Implement the application architecture so that GraphSAGE can produce:

Node / Function → Suspicion Score 

Example:

parse_input()       0.31 validate_input()    0.18 compare_token()     0.94 process_payload()   0.71 main()              0.11 

The system should use these scores to identify areas requiring deeper analysis.

Do not hardcode the final GNN results into the product architecture.

For the prototype, the GNN module may initially be represented by a service interface/stub, but the architecture must allow the real GraphSAGE implementation to be connected later without rewriting the frontend.

Timing Side-Channel Analysis

Create a dedicated timing analysis workflow.

VARUNA should support:

Selecting a target function

Running timing measurements

Collecting timing distributions

Comparing input groups

Running Welch's t-test

Displaying the statistical result

Flagging potential timing leakage

Applying a patch

Re-running the same timing analysis

Comparing before/after results

Display evidence clearly.

Example:

BEFORE PATCH  Samples: 20,000 t-statistic: 18.42 Status: POTENTIAL LEAKAGE   AFTER PATCH  Samples: 20,000 t-statistic: 1.37 Status: NO SIGNIFICANT LEAKAGE 

Do not invent statistical results.

All values shown in the interface must come from the backend analysis engine or clearly labelled demo data.

Patch Re-Verification

This is one of the most important parts of VARUNA.

After applying a patch:

Run the same security test again.

For timing vulnerabilities:

Original implementation → timing test → leakage detected  Patched implementation → same timing test → compare results 

For protocol vulnerabilities:

Original parser → fuzzing → crash  Patched parser → same/relevant fuzzing campaign → crash signal removed or reduced 

Also run applicable:

ASan

UBSan

Regression tests

Existing unit tests

Show the evidence rather than simply displaying “Fixed.”
